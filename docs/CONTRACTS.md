# Shared implementation contracts

Product authority: `PRODUCT_SCOPE.md` records the user's October 2 scope correction. The broader domain/API catalog below includes legacy compatibility code; it is not the active product requirements list.

Role consideration: `redeployments.data.considerForRoles` is boolean. Existing published records with the field absent remain considered; newly created records default to true. Changing consideration or enabling/disabling publication requires the scoped planning operation `redeployments / FLAG_FOR_ROLES` in addition to the applicable CRUD operation. HR grants may use org/subtree scope; manager grants may use reports scope rooted at the manager's worker ID. Role labels and employee initiation are not required or sufficient. Imports call the same mutation enforcement. `GET /api/records/redeployments?considerForRoles=true|false` filters effective consideration; matching and overview use the same rule. Flag changes are persisted as dated revisions with actor IDs in history/audit.

Consideration changes default to today's decision date unless an explicit effective start is supplied. Authorization uses the reporting relationship at the decision date, so a newly assigned manager can change a previous manager's flag. `getRecord(actor,domain,id,date?)` and `GET /api/records/[domain]/[id]?date=` select the effective revision and enforce READ at the requested date; omitting date retains the existing current-head behavior. Drawers and reference labels use their planning date. Historical salary/identity reads still require their separate data-class grants.

Lean architecture: Next.js App Router + strict TypeScript; `pg` with parameterized SQL, PostgreSQL migrations; `zod` schemas; TanStack Table; Tailwind; `openid-client` v6. Native PostgreSQL transactions, row locks, exclusion constraints and durable jobs. Monetary/FTE math uses `decimal.js`. UUID identifiers; all end dates exclusive.

Retention handoff: `POST /api/team-needs` accepts `{record: CREATE mutation, skillIds: UUID[]}` and atomically creates a demand and its required skills through the same scoped mutation checks. A denied or invalid skill rolls back the demand. `POST /api/transfers` accepts `{placementId,demandId,destinationManagerId,effectiveFrom,reason}`. The server reads authorized records and captures source assignment, worker, placement and demand versions. Movement fields `workerVersion`, `placementId`, `placementVersion` and `destinationManagerId` supplement the existing source/request baseline fields. The team request must be approved before proposing a permanent transfer.

Permanent `movements / commit` transfers the whole primary allocation, updates the worker's home org on the effective date, ends old reporting lines and creates the destination manager relationship. It creates an approved fulfillment and clears consideration with state `placed`; there is no source allocation restored later. Fulfillment ends at the earlier existing employment/request end; the destination assignment preserves an existing employment end. Worker employment status and identity/pay values are unchanged. A placed consideration record can be flagged again as a dated active revision of the same stable ID, with the receiving manager's decision-date rights.

The commit is transactional and revalidates baselines, dates, approved demand, confirmed movable capacity, allocation/constraint conflicts and fulfillment limits. Competing proposals serialize on the worker and demand locks. Future home-record revisions and capacity that cannot cover the employment period require a revised proposal. Identity, directory accounts, external identifiers, contracts, hired-for, worker skills, compensation, reveals and redeployments require explicit `TRANSFER_SCOPE` in both org scopes and their separate data classes. This operation permits metadata relocation without identity/salary READ or changing their field values. Existing reveal approvals are revoked on the transfer date. Ordinary worker/assignment/reporting/fulfillment mutation permissions and `FLAG_FOR_ROLES` remain required. The response contains the movement and operation impact, not protected records; audit metadata contains no identity or salary values.

## Database infrastructure (root)

All domain tables have `id uuid, tenant_id uuid, org_id uuid null, worker_id uuid null, valid_from date, valid_to date null, version integer, state text, data jsonb, created_at timestamptz, updated_at timestamptz`, `(tenant_id,id)` unique. Views must explicitly project permitted fields. `record_history(tenant_id, domain, record_id, version, snapshot jsonb, actor_id, created_at)` is restricted, not public generic CRUD. `tenants(id,name,settings jsonb,auth_version int)`; `principals(id,tenant_id,entra_object_id,roles jsonb,enabled bool,auth_version int)`; `sessions(id,tenant_id,principal_id,token_hash,expires_at,auth_version,entitlements_checked_at)`; `access_grants(id,tenant_id,principal_id,domain,operation,data_class,org_id,scope,valid_from,valid_to)`; `group_mappings(id,tenant_id,group_id,app_role,domain,operation,data_class,org_id,scope,enabled)`; `audit_events`, `jobs`, `sync_connections`, `sync_runs`, `sync_checkpoints`, `import_batches`, `import_rows`, `export_files` as migration defines. Agent can supply additive migrations 002 integration, 003 imports to own tables. Shared infra base definitions may be coordinated.

## HTTP (root routes; UI consumes)

`GET /api/records/[domain]?date=&orgId=&search=&state=&page=&pageSize=` returns list; `GET /api/records/[domain]/[id]` returns row; `POST /api/records/[domain]` accepts mutation. `GET /api/history/[domain]/[id]` history subject to same protected permissions. `POST /api/actions` accepts `{action,domain,id,version,...}`; actions submit, approve, reject, return, cancel, commit, fork, restore-version, reveal, revoke, resolve, simulate. `GET /api/overview` returns real scoped metrics, quality/backlog. Errors `{error:{code,message}}` with no stack. Writes same-origin protected.

`GET /api/imports/templates?domain=&format=csv|xlsx&example=true|false`; `POST /api/imports/preview` multipart file/domain/operation/mode/mapping; `POST /api/imports/commit` JSON batchId/hash; `GET /api/imports/[id]`; `POST /api/imports/reverse` JSON batchId. Imports agent owns these routes and exports endpoint `/api/exports` with domain/format/date/orgId query. Export only accessible domain rows, no leaked identity joins.

Integration agent owns `/api/auth/login`, `/api/auth/callback`, `/api/auth/logout`, `/api/admin/[action]` for settings/connection-test/sync/pause/resume/manager-refresh/group-refresh/mappings/grants/revoke/simulate; all admin checks server side, deny identity/salary by default. May coordinate names with UI agent. UI pages consume APIs and use getActor/listRecords server side where practical.

Responses cache-control no-store; identity/compensation never mixed into masked views. Background jobs reload actor and permissions at execution; never accept client-supplied tenant/role/grants. Live providers remain inactive until explicitly configured by administrator.
