# Entra ID and Microsoft Graph setup

The application has no demo authentication route. Configure a tenant before sign-in. It uses tenant-specific OpenID Connect discovery, authorization code flow with PKCE, one-use database-backed state/nonce transactions, explicit ID-token JWS signature verification through openid-client v6, issuer/audience/expiry checks, and opaque database sessions. Tokens and secrets are never persisted in application domain records or returned to the browser.

Set server environment variables `APP_URL` (HTTPS origin), `ENTRA_ALLOWED_TENANTS` (comma-separated tenant GUIDs), `ENTRA_CLIENT_ID`, and `ENTRA_CLIENT_SECRET`. Register `${APP_URL}/api/auth/callback` as a Web redirect URI. Secure `__Host-` cookies require HTTPS in development too. Provision the tenant row and the initial administrator grants through controlled database administration; no first-user privilege escalation is implemented. A verified identity without an effective grant cannot enter the application. App roles do not independently authorize actions: each must have an explicit role mapping to domain, operation, data class and organization scope. OIDC app-role changes are picked up on sign-in; application revocation is immediate, and sessions expire after eight hours. If immediate external role revocation is required, use group mappings and the scheduled entitlement refresh rather than role-only access.

Use a separate application registration for Graph with `GRAPH_CLIENT_ID` and `GRAPH_CLIENT_SECRET` available only to the server/worker. Grant the read-only application permissions `User.Read.All` and `GroupMember.Read.All`, with tenant admin consent. There is no directory write API in the adapter. Secret storage should be backed by the deployment secret manager; rotate credentials there. The supplied implementation uses client-secret credentials; managed identity/certificate credentials require an additional credential provider.

The admin Settings operation creates a paused connector. Set explicit inclusion group GUIDs and the guest policy, run Connection test, then Resume and enqueue Sync. An empty inclusion-group list means all tenant members; guests are excluded unless explicitly enabled. No live calls are made before administrator configuration and worker execution. The credential token endpoint is fixed to the selected tenant and public Microsoft cloud. Sovereign cloud support needs a separately reviewed endpoint configuration; arbitrary origins are rejected.

Jobs are `graph.sync`, `graph.groups`, and `graph.managers`, consumed by `processGraphJob({id,tenant_id,kind,payload}, actor)`. A current tenant actor with `settings / ADMIN / configuration` access is required. Each directory page and its continuation are committed together, with permission rechecks and an audit. The original `nextLink`/`deltaLink` is preserved and restricted to HTTPS, graph.microsoft.com, and the expected resource path; redirects, userinfo, fragments, and host changes fail closed. Empty pages continue. HTTP 429/5xx use bounded Retry-After/backoff retries; longer waits and exhausted retries fail the job for the durable worker retry policy. HTTP 410 restarts a full generation and reconciles missing projections only after the final page. A tenant must have at most one active Graph sync/entitlement job, enforced by worker serialization. Graph and sync tables enforce PostgreSQL tenant RLS; OAuth browser transactions are bootstrap records addressed by an opaque token hash.

Graph owns `graph_directory_projection`, `graph_manager_projection`, and `graph_group_memberships`. It creates linked directory accounts and, when a department has an approved organization mapping, an initial masked worker and separate protected identity. `POST /api/admin/department-mapping` accepts `{department,orgId}` and requires organization administration permission. Missing mappings and pre-existing unlinked accounts create reconciliation items. Names and email addresses are never used as matching keys. New workers use `manual-only` type pending employment evidence and have no assumed contract or capacity. Initial records and subsequent linked directory changes receive version history, field provenance, and audits. Existing worker, identity, home organization, title, contract, reporting line, availability, skill and compensation values remain application owned. Titles stay directory metadata until a steward resolves the canonical role. Directory deltas preserve omitted properties. Deleted/disabled accounts invalidate sessions and cannot be reactivated by a later group refresh.

Manager refresh uses its own tenant-scoped `graph_manager_checkpoints` cursor (migration 005). Each observation and cursor advance commit together. An interrupted scan resumes at the first uncommitted object; completing a cycle marks it complete, and the next invocation begins a new generation. A fixed upper object-ID bound keeps each cycle finite; accounts arriving behind the cursor wait for the next cycle. Permission and connector-state checks precede remote reads and commit. Manager `checked_at` records last observation time. `resolution` distinguishes a returned manager (`resolved`), HTTP 404 (`missing`, which does not prove the user was deleted), and inactive or removed source accounts (`inactive`). Missing/inactive observations clear the stored manager ID; other Graph errors fail without advancing. Existing projections for inactive or absent users are included for cleanup. Business reporting lines and their effective history are never rewritten. Raw manager observations currently retain only the latest value, not temporal history or automatic conflict reconciliation.

The adapter retains per-user `/users/{id}/manager` requests. The current [Microsoft List manager documentation](https://learn.microsoft.com/en-us/graph/api/user-list-manager?view=graph-rest-1.0) lists application permissions as unsupported, while this connector uses client credentials. Consequently, manager refresh is not established as operational with the configured app-only credentials: a supported authentication/read strategy and authorized live-tenant acceptance remain required. A 403 fails closed and leaves the cursor resumable; synthetic tests do not prove live permission support.

Linked directory metadata updates consult current effective `field_policies`. Policies must match the tenant and, when specified, the account's exact organization and worker; more specific policies take precedence over tenant defaults. Fields owned by application, HR, or Finance are preserved and conflicting source updates create reconciliation items. An override requires the exact directory record and organization, a matching worker when specified, approved state, a reason, current effective dates, a future exclusive expiry date, and an Entra policy with `overrideAllowed=true`. Scalar strings are converted using the field's registry type; invalid values or multiple active overrides are flagged instead of selected arbitrarily.

The original upstream values remain in `graph_directory_projection`. Every successful `graph.sync` runs a bounded sweep of linked override targets, even after an empty delta, so expired or cancelled overrides can return to the latest cached source value. Expiry creates a deduplicated reconciliation event. If a field now belongs to another source, the sweep preserves its current value and raises an ownership conflict for a steward. A paused or failing connector delays the sweep until a successful sync; schedule sync at the required operational cadence. History and field provenance record applied overrides and their removal, while audit and reconciliation metadata exclude field values. Authorization and account revocation continue to use the authoritative identity records regardless of a directory display-field override.

Supported override targets are source-backed directory fields (`enabled`, `userType`, `lastSeen`, `directoryTitle`, and `directoryDepartment`). The stable `objectId` cannot be overridden. `employeeId` is not collected in the current projection, so an override for it is flagged as unsupported rather than applied without a recoverable source. Worker, assignment, and compensation records are not changed by this override path.

Sensitive identity, salary, and cost grants/mappings are staged in `sensitive_access_requests`. `POST /api/admin/approve-access` accepts `{requestId}` and requires a different approver with domain-specific administration access. The approver cannot be the grant target or a known member of the mapped group/role; group approval requires a recent completed snapshot of that specific group. Pending mapping groups are included in group refresh. Revocation is immediate and invalidates affected session authorization versions.

Entitlements use transitive group membership. Membership pages are checkpointed. Grants are atomically replaced after all configured groups are fetched, removed grants stop authorizing on the next request, and principals with no remaining grants lose sessions. Group-based grants expire closed if the entitlement snapshot is over fifteen minutes old; schedule `graph.groups` at least every five minutes. Failure never extends freshness. Manual and role grants are intentionally independent and may continue to authorize a former group member. Revoking a principal disables the account, removes every grant, and deletes its sessions. Re-enabling after directory disable requires explicit administration.

Login grant materialization also requires the exact group's completed checkpoint, matching membership generation, and fifteen-minute freshness. A partial page cannot confer access using the freshness of a previous global refresh. A login during an incomplete group refresh may therefore lose group access until that group finishes. Removed group grants advance the principal's authorization version, including when a separate manual grant permits the login. Verified role removals and stale-session deletion commit even when the resulting login is denied for having no grants. Full directory reconciliation disables principals absent from the completed scan and advances their authorization version as well as deleting browser sessions; retained worker/business records remain unchanged.

Tests use synthetic identifiers and fake Graph pages. They do not establish tenant consent, production connectivity, or a successful live sign-in. Production acceptance requires an authorized test tenant, database migrations, HTTPS, secret configuration, a least-privilege deployment role, OIDC callback/replay rejection, group removal, worker restart, and backup/recovery checks.
