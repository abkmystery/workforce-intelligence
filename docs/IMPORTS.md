# Imports and exports

The import template is generated from `src/lib/registry.ts` for every registered domain. `GET /api/imports/templates?domain=<key>&format=csv|xlsx&example=true|false` returns template version 1. XLSX files contain a `Data` sheet, a `Dictionary` sheet with field types, required and nullable flags, and an `Instructions` sheet. CSV has the same `Data` columns. The supported domains are all registry keys; protected identity and compensation fields remain in their respective domains and require their own grants.

The system columns are `_id`, `_version`, `_org_id`, `_worker_id`, `_valid_from`, and `_valid_to`. Field columns use registry keys. For updates, omitted or blank cells leave values unchanged. `0` and `false` are values. `<CLEAR>` sets a nullable field to null. `CREATE` requires required fields and `_valid_from`; `UPDATE`, `ARCHIVE`, and `RESTORE` require `_id` and `_version`. `UPSERT` creates when `_id` is blank and updates when supplied. `VALIDATE_ONLY` previews the same create/update interpretation and cannot be committed. All dates use ISO `YYYY-MM-DD`, with an exclusive end date.

`POST /api/imports/preview` accepts multipart `file`, `domain`, `operation`, `mode` (`ALL` or `SELECTED`), and optional JSON `mapping`. It returns `{batchId,hash,status,rowCount,validCount,rows}`. Each row has `rowNumber`, `values`, `errors`, `status`, and a before/after `diff` for valid rows. Each candidate mutation runs through the central record service under a PostgreSQL savepoint; the savepoint is rolled back before the batch is persisted. This checks domain validation, references, dating and permissions without keeping the trial write. The parsed rows, errors, preview fingerprint, schema fingerprint, actor and permission fingerprint are persisted. Preview requires `IMPORT` and the underlying operation grant on each target. Existing targets also require record read access for preview. The batch can be inspected at `GET /api/imports/[id]`.

`POST /api/imports/commit` accepts `{batchId,hash,selectedRows?}` and queues a durable `IMPORT_COMMIT` job. `ALL` requires every row to be valid. `SELECTED` requires explicit unique valid row numbers. A repeated commit for a queued, processing, or completed batch returns its existing job. The worker reloads the actor, verifies schema and permission fingerprints, locks the batch and target records, checks version and grants again, and commits selected mutations and outcomes in one transaction. A failure rolls back all selected changes and marks the batch failed. `POST /api/imports/reverse` accepts `{batchId}` and reverses a completed batch in reverse row order in one transaction, after checking the current version and permissions. It rejects states or fields that cannot be safely restored through the record mutation service.

Uploads are bounded to 5 MiB, 25 MiB total XLSX expanded ZIP content, 1,000 ZIP entries, and 5,000 data rows. Only UTF-8 CSV and XLSX are accepted. The parser rejects duplicate columns and rows, unknown columns, malformed values, formula-like cells, XLSX formulas, hyperlinks, and XLSX archives containing macros, external links, connections, or embeddings. The record service applies domain validation and concurrency rules at commit. Import rows are stored in PostgreSQL and are accessible only to the batch actor under the original permission fingerprint.

`GET /api/exports?domain=<key>&format=csv|xlsx&date=<ISO>&orgId=<uuid>` exports rows visible under both `READ` and `EXPORT` scope. Field values come from the domain record service; no identity or pay join is added. Spreadsheet values beginning with a formula trigger character are prefixed with an apostrophe. Exports are bounded to 50,000 rows, and metadata is logged in `export_files`.

`POST /api/exports` accepts `{domain,format,date?,orgId?}` from the same origin and creates a private Azure Blob artifact. It returns `{exportId,expiresAt,downloadPath}`; `createStoredExport(actor,input,storage?,stableExportId?)` is also available to a future scheduled-export worker. The optional fourth argument is internal only; it must be a UUID. A retry with the same ID returns the original artifact only when tenant, owner, domain, format, pinned effective date, org filter, authorization version, effective grant fingerprint and expiry still match. Scheduled callers must pass an explicit `date` for retries that may cross midnight. Concurrent attempts upload to distinct private Blob keys; the database insert selects one winner, and the losing attempt removes only its own Blob. `GET /api/exports/[id]` sends the artifact through the authenticated application; no SAS or Blob URL is returned. Downloads require the original owner, current enabled principal and authorization version, still-effective `READ` and `EXPORT` grants with the same permission fingerprint, and an unexpired 24-hour artifact. Before reading Blob bytes, the server rebuilds the current permission-filtered export for the recorded effective date and org filter and rejects a changed record fingerprint, including changes caused by org or reporting-line scope. It checks expiry again after Blob download and verifies stored byte count and SHA-256 before responding. Artifact keys contain opaque tenant and artifact UUIDs; audit entries contain export IDs and counts, never record contents. The Blob container must already exist and report no public access on every upload/download. Runtime credentials come from the Container App's user-assigned managed identity through `DefaultAzureCredential`, using `AZURE_STORAGE_ACCOUNT_URL`, `AZURE_EXPORT_CONTAINER`, and `AZURE_CLIENT_ID` set to that identity's client GUID. Stored artifacts are capped at 25 MiB. No local filesystem fallback or public download URL exists.

Current implementation limits: imports and direct exports remain buffered in application memory; stored exports are buffered before upload and after download. The 24-hour expiry is enforced on download; periodic deletion of expired Blob objects is not wired to the worker yet and must be configured as an Azure Blob lifecycle rule or future cleanup job. There is no virus scanner. The XLSX parser reads one `Data` sheet per batch; it does not coordinate domain records across multiple workbook sheets. ZIP expansion is bounded before parsing, but no external malware/content scanner is integrated. The 5,000 row parser limit and 50,000 row export limit are operational caps, not throughput guarantees. Import history and reversal depend on the record service's mutation rules; a reversal can be refused when intervening edits, approval state, or a nonnullable field prevent exact safe restoration. Background import processing requires the PostgreSQL worker and configured database. Scheduled export job wiring is not implemented.
